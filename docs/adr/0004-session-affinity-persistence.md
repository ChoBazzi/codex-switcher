# 0004. 세션 어피니티 영속화 및 2주 정리 정책

- 상태: accepted
- 날짜: 2026-09-05

## 결정 배경

개발자의 일반적인 작업 패턴은 터미널 창(Codex CLI 세션)을 상시 열어두고, 맥북을 잠자기(Sleep)로 전환하며 수시로 작업을 재개하는 형태이다.
만약 프록시가 단기 인메모리 타이머(예: 30분, 2시간)로 세션 어피니티를 관리하면, 잠자기에서 깨어나 동일 터미널 창에서 추가 질문을 입력했을 때 세션 정보가 소실되어 OpenAI 서버로부터 `404 / Invalid response ID` 오류가 발생하거나 대화 맥락이 끊어진다.

## 검토한 선택지

1. **단기 인메모리 유휴 타이머 (30분~2시간)**:
   - 구현은 단순하나, 맥북 잠자기 후 복귀 시 세션 매핑이 만료되어 대화 연속성이 파괴됨.
2. **로컬 SQLite 영속화 + 2주(14일) 정리 정책 (선택)**:
   - 세션 매핑(`session_id`, `response_id` ↔ `account_id`)을 로컬 SQLite에 저장.
   - 맥북이 잠들거나 프록시가 재시작되어도 동일 CLI 세션은 기존 계정에 확고히 유지.
   - 마지막 요청 후 2주(14일) 동안 활동이 없는 세션만 만료 및 정리.

## 최종 결정

2026-09-09: 모든 전환에 새 세션을 요구하는 정책은 [ADR 0040](0040-same-conversation-switch-and-optional-wiki.md)에서 부분 대체한다. 서버 continuation 소유권 검증과 기존 영속 기록 보호는 유지한다. 실험의 같은 대화 전환이 영속 라우터까지 구현됐다는 의미는 아니다.

**2번: 로컬 SQLite 영속화 및 2주(14일) 유휴 정리 정책**을 채택한다.

- 세션 어피니티 정보는 로컬 SQLite에 보관하여 프로세스 재시작 및 시스템 잠자기에도 보존한다.
- 동일 CLI 세션에서 이전 대화를 이어가는 요청(continuation 참조)은 시간 경과와 무관하게 기존 계정으로 라우팅한다.
- 명확한 한도 소진 또는 수동 전환 시 다음 세션용 계정을 준비한다. ADR 0009에 따라 원본 세션 매핑은 유지하고 사용자 입력 이후 새 세션을 대상 계정에 연결한다.
- 잠자기 동안 계정의 사용량 리셋 시간이 지난 경우, 별도의 대화 단절 없이 기존 계정의 충전된 한도로 매끄럽게 작업을 이어간다.
- 세션 정리(GC)는 마지막 요청 시각 기준으로 14일(2주)이 경과한 데이터에 한해 수행한다.
- GC 이후 소유권을 확인할 수 없는 continuation은 신규 요청으로 간주하여 다른 계정에 보내지 않고 차단한다.

## 예상되는 결과와 장단점

구현 단계: ADR 0017에서 SQLite 저장소 및 영속 라우터를 추가했다. 실제 프록시의 요청 의도/응답 관찰 연결과 주기 GC 호출은 아직 후속 단계이며, 현재 demo/live-test에는 자동 적용되지 않는다.

### 장점
- 터미널을 상시 켜두고 맥북을 여닫는 실무 워크플로우에서 대화 맥락이 완벽히 보존된다.
- 프록시 데몬 재시작에도 세션 바인딩이 유실되지 않는다.

### 단점
- SQLite I/O가 수반되나, 세션 매핑 수준의 데이터는 SQLite로 처리 시 밀리초 이하의 무시할 수 있는 오버헤드에 불과하다.
