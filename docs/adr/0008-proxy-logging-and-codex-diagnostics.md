# 0008. 프록시 독립 로그 기록과 Codex 진단

- 상태: accepted
- 날짜: 2026-09-05

## 결정 배경

계정 선택, 인증 갱신 및 전환 실패 원인은 프록시 내부에서 발생한다. Codex는 자신이 받은 결과만으로 내부 처리 과정을 알 수 없으며 한도 소진이나 CLI 종료 시에도 진단 기록이 필요하다. 로그 기록 자체에 추론 토큰을 사용하지 않는다.

## 검토한 선택지

1. Codex에 로그 작성을 맡김: 프록시 내부 관측이 제한되고 CLI 실행 및 모델 가용성에 의존한다.
2. Go helper가 직접 기록하고 Codex가 필요할 때 진단 파일을 분석함 (선택): 기록을 독립적으로 유지하고 분석 범위를 제한할 수 있다.

## 최종 결정

- Go helper는 JSON Lines 형태로 요청 수신·완료·오류, 계정 선택, 토큰 갱신 결과, 전환 시도·결과 및 helper 상태를 기록한다. SSE 토큰 단위 기록은 하지 않는다.
- 시각, 심각도, 이벤트, 앱 내부의 불투명 request/session/account/switch 식별자, attempt, 요청 진행 단계, HTTP 상태, 정규화된 오류 코드와 처리 시간을 허용 필드로 사용한다. 해당하지 않는 필드는 생략한다.
- 요청 진행 단계는 전송 전, upstream 전송 시작, CLI 응답 시작, 완료, 결과 불명 등을 구분한다. 단순 전송 기록을 서버 실행 완료 증거로 취급하지 않는다.
- 인증 헤더, access/refresh token, 실제 계정·서버 대화 식별자, 이메일, 인증 URL, 로컬 경로 및 본문은 기록하지 않는다. 본문에는 대화, 도구 인자·결과와 Wiki 내용도 포함된다.
- upstream 오류나 예외 문자열을 그대로 출력하지 않는다. 허용 필드 구성과 사유 정규화를 기록 전에 수행한다.
- 사용자가 필요할 때 범위를 제한한 진단 파일을 내보내 Codex에 제공한다. 내보내기에서도 허용 필드를 재검사하며 Keychain, 인증 파일과 원본 세션 기록을 포함하지 않는다.
- 진단 로그를 자동으로 프롬프트에 넣거나 오류마다 LLM 분석을 요청하지 않는다. Codex 분석은 프록시 운영이나 자동 전환의 필수 경로가 아니다.
- Codex CLI는 대화·도구 실행 기록을, Wiki 계층은 작업 인계 내용을 담당한다. 프록시 로그는 두 기록의 대체물이 아니다.
- 로그는 로컬 사용자 전용 권한으로 관리하고 크기·보관 기간에 따라 순환한다. 구체적 저장 경로와 한도는 구현 시 정한다.
- 로그 I/O가 스트리밍을 무기한 막지 않도록 하고 기록 실패·누락을 상태로 노출한다. 로그 쓰기 실패만으로 추론 요청을 재전송하지 않는다.

## 예상되는 결과와 단점

- Codex 한도 소진이나 UI 종료 중에도 실행 중인 helper가 오류를 기록한다.
- 동일 요청·전환의 시도와 결과를 연결해 원인을 분석할 수 있다.
- 로그 기록은 LLM 토큰을 쓰지 않으며 Codex가 진단 파일을 읽고 분석할 때는 토큰이 소비된다.
- 원문을 제외하므로 일부 문제의 상세 재현에는 합성 fixture나 별도 호환성 검증이 필요하다.
- 프로세스 강제 종료나 저장 장치 오류에서 마지막 이벤트까지 보존되는 것은 보장하지 않는다.

## 검증 기준

- 합성 한도 소진 및 전환 실패를 발생시키고 상관관계 식별자로 처리 경로를 확인한다.
- 헤더, upstream 오류 본문과 예외에 합성 비밀값을 삽입하고 로그·진단 파일에서 제외되는지 확인한다.
- CLI와 UI가 없어도 helper가 기록하며, 기록만으로 LLM 요청이 발생하지 않는지 확인한다.
- 로그 로테이션·쓰기 실패 시 요청 중복 전송과 무기한 스트리밍 지연이 없고 기록 누락 상태가 표시되는지 확인한다.
