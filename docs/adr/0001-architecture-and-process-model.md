# 0001. 아키텍처 및 프로세스 모델 (SwiftUI + Go Helper)

- 상태: accepted
- 날짜: 2026-09-05

## 결정 배경

Codex CLI의 실행 중단 없이 계정을 전환하려면 로컬 역방향 프록시가 항상 안정적으로 동작해야 한다. 동시에 macOS 메뉴바에서 계정별 사용량을 확인하고 수동 전환을 제어할 수 있는 네이티브 UI가 필요하다.

단일 앱 프로세스로 모든 것을 처리할 경우, 메뉴바 앱이 비정상 종료되거나 사용자가 재시작했을 때 실행 중인 CLI 세션 및 스트리밍 연결이 함께 끊어지는 문제가 발생한다.

## 검토한 선택지

1. **단일 Swift/SwiftUI 앱**: 메뉴바 UI와 로컬 프록시 서버를 단일 macOS 앱 내에서 통합 실행.
2. **단일 Go 앱 + Web/Systray UI**: 모든 로직을 Go로 작성하고 간이 시스템 트레이 또는 웹 뷰 사용.
3. **SwiftUI 메뉴바 앱 + Go 프록시 헬퍼 독립 데몬 (선택)**: UI는 Swift/SwiftUI로, 프록시 및 동시성 처리는 독립 Go 프로세스로 분리하고 loopback Control API로 통신.

후속 [ADR 0054](0054-independent-proxy-service.md)에서 앱과 모델 프록시 수명을 분리했다. 앱 서비스 제어는 사용자 전용 Unix 소켓, 시작은 최초 연결 시 detached 프로세스로 구체화하며 로그인 시 자동 시작은 보류한다. 토큰 갱신은 [ADR 0053](0053-helper-token-refresh.md)을 따른다.

## 최종 결정

**3번: SwiftUI 메뉴바 앱 + Go 프록시 헬퍼 듀얼 프로세스 구조**를 채택한다.

- **SwiftUI 앱**: `MenuBarExtra`, 사용자 제어와 상태 표시 등 macOS 네이티브 경험 전담.
- **Go Helper**: HTTP 역방향 프록시, SSE 중계, Keychain 인증 읽기·저장, 토큰 갱신(single-flight), 라우팅 및 세션 어피니티 전담. Keychain 연동은 helper에서 사용할 수 있어야 하며 UI 프로세스에 의존하지 않는다.
- **생명주기**: 사용자 세션의 독립 백그라운드 서비스로 시작하고 단일 인스턴스를 유지한다. UI 종료가 helper 종료를 의미하지 않는다. 업데이트는 진행 중인 요청을 마친 뒤 적용하며 장애 후 실패 요청은 재생하지 않는다. 등록·자동 시작·서명 및 Keychain 접근은 구현 시 검증한다.
- **전환**: ADR 0009에 따라 다음 세션용 계정을 준비하고 사용자 입력을 기다린다. 실패 요청 자동 재시도는 금지한다.
- **통신**: `127.0.0.1` 한정 Control API(HTTP) 및 이벤트 스트림(SSE)을 사용하며, 로컬 bearer secret으로 보호한다.

## 예상되는 결과와 장단점

### 장점
- UI 앱이 재시작되거나 충돌해도 백그라운드 프록시와 활성 CLI 스트림이 유지된다.
- Go 언어의 우수한 네트워크 I/O 및 동시성 모델을 활용해 프록시 안정성을 확보한다.
- 메뉴바는 SwiftUI가 처리하고 인증은 UI 없이 동작하는 helper가 소유한다.

### 단점
- 두 프로세스 간 통신 프로토콜(Control API) 및 프로세스 수명주기(시작/종료/헬스체크) 관리 비용이 발생한다.
